## Learned Rules

Standing rules mined from past corrections; each exists because the same mistake was made and corrected at least once.

### Tooling & environment

- **AI-tooling config changes land in the Nix source, not the live config** (skills, instructions, MCP, settings are generated by this repo): change the module, then `./nix.sh`, never hand-edit `~/.claude/settings.json` or `~/.claude/rules/workflow.md`.
- **The AI stack is Claude Code in the terminal, nothing else**: don't propose Claude Desktop, new AI CLIs or extra LLM clients.
- **Changes land in the user's working tree**: worktrees are for isolation during work, the result must be applied to the actual project before claiming done.
- **Worktrees are temporary**: non-trivial feature work in one, quick fixes directly in the working tree, every worktree removed as soon as the work lands.
- **Never swap build tooling or framework infrastructure as a side effect**: Bundler, server runtime or framework changes need their own explicit approval and a rollback plan.
- **Do the work yourself**: never reach for another model or a paid API for translation, content or analysis the assistant can do directly.

### Following instructions

- **A pasted link is an instruction, not decoration**: fetch it, use it, say what you took from it.
- **A revert is complete**: files, dependencies and tools added for the change all go, and later work that built on the reverted code is re-verified.
- **No loops**: the same command failing twice means stop, change approach or ask, never re-run unchanged hoping for a different result.
- **A config change isn't done while an old contradicting block survives**: find and remove or flip the rule that blocks the new behavior, don't add a new one beside it.
- **Check official docs for a fast-moving library before implementing, unprompted**: training memory lags releases; the stack skills (`personal-stack`, `ts-conventions`) name which libraries this bites on.
- **A PR isn't delivered with conflicts on it**: after opening, updating, or the base moving, resolve immediately and confirm mergeable.
- **Never name a new thing for a problem an existing name already covers**: search for the value first, delete a duplicate before adding a name, and repeat a literal at three call sites rather than add a fourth name nobody will find.

### Docs style

- **No counts or ranges in docs that go stale**: describe the set, not its size ("architecture decision records, numbered", not "ADRs 0001–0014").
- **Never hard-wrap prose in Markdown a human reads in a renderer**: one line per paragraph, however long; a hard break renders as a visible line break. Instruction, skill and agent files are not exempt.

Stack-specific style rules are **not** here; they live in the `ts-conventions`, `react-conventions` and `api-conventions` skills so they cost nothing in a Nix or content session. Load the matching skill before writing code.

### Git & repo hygiene

- **In a repo with the user's uncommitted work, commit with an explicit pathspec**: plain `git commit` sweeps whatever the user had staged into your commit (this has happened more than once). `git commit -m … -- my-file`, or verify `git diff --cached --stat` first.
